# 数据存储：从 PGlite 迁到真 Postgres（2026-10-01）

## 为什么换

线上原来用 **PGlite**（WASM Postgres，`DATABASE_URL` 不配时的默认值，数据在 `.openmuse/postgres`）。
它是单进程玩具级方案，而本服务是**长驻 + 频繁重启**：写入途中被 `systemctl restart` 打断会留下撕裂的数据。
一天内真实踩到三次，每次都表现成"接口 502、原因看不见"：

1. `missing chunk number 0 for toast value 16631 in pg_toast_16384` —— 某行的 TOAST 大字段缺块；
   而 `list`/`scan` 是**一条 SELECT 扫全表**，TOAST 在扫描到那一行时才读 ⇒ 一行坏数据让整张表读不出来 ⇒ `/api/agent` 整体 502。
2. `heap tid from index tuple (43,30) points past end of heap page line pointer array … in index "records_pkey"` —— 主键索引指向不存在的行。
3. `could not create unique index "records_pkey"` —— 表里出现**重复主键**。

代码侧已做两处加固（仍在）：日志不再只打 `error.name`（补齐 message + 前 8 行栈 + 令牌脱敏）；
`list`/`scan` 命中损坏行时降级为按 `ctid` 逐行读、坏的跳过。但**根因是存储选型**，所以换库。

## 现在的形态

- **PostgreSQL 18**（Ubuntu 包，systemd 集群 `main`，5432，`enabled` 开机自启）。
- 连接串在仓库根 `.env`（600、已 gitignore）：`DATABASE_URL=postgres://openmuse:…@127.0.0.1:5432/openmuse`。
  Store 走 `pg` 分支，启动时 `CREATE TABLE IF NOT EXISTS records(...)`，schema 与 PGlite 时代完全一致。
- 旧目录 `.openmuse/postgres/` **保留未动** —— 它是回滚路径（把 `.env` 的 `DATABASE_URL` 去掉即回到 PGlite）。
- 迁移脚本：`scripts/migrate-pglite-to-postgres.mts`（按 `ctid` 逐行读、坏行跳过、保留 `updated_at`、upsert 幂等，可中断重跑）。

### 迁移过程（实测数字）

```
停机 → 备份 → npx tsx scripts/migrate-pglite-to-postgres.mts
  源库 983 行，按 ctid 逐行读（损坏行会跳过）
  迁移完成：搬过去 983 行，跳过 0 行，目标库现在 983 行
  抽样 worker-status/tasks、agent-settings/identity、ideas/… 与源库一致: true
起服务 → GET /api/agent 200（29 个任务）→ 派一个真任务跑完 succeeded → 目标库 983 → 991 行
```

## 备份

- `openmuse-pg-backup.{service,timer}`：每天 04:30 UTC 跑 `/usr/local/bin/openmuse-pg-backup.sh`，
  `pg_dump | gzip -9` 写到 `/home/ubuntu/backups/openmuse-<UTC 时间戳>.sql.gz`（600），保留最近 7 份。
- **验证过恢复**：把最新 dump 灌进临时库 `openmuse_restoretest` → 991 行，与线上一致 → 删掉临时库。
  （"没恢复过的备份不算备份"，这一步以后每次改 schema 前都该做。）

```bash
ls -lh /home/ubuntu/backups/
systemctl list-timers openmuse-pg-backup.timer
sudo systemctl start openmuse-pg-backup.service     # 手动跑一次
```

## 仍然要注意

- 迁移脚本的抽样校验是拿**源快照**与**目标库**比对：如果服务在跑（目标库继续写入），这几行会显示 `false`，
  那是"目标更新了"，不是迁移失败。**停机迁移时应当全是 true**。
- 真 Postgres 之后，`db.ts` 里那套"逐行降级"基本不会再触发；留着是为了面对任何单行异常时界面不整体 502。
