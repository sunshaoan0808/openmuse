# 任务流展示：我们和 Muse 原版差在哪、为什么

> 结论先行：**差距不在样式，在模型层。** Muse 的客户端拿到的是**"一次跑动"的任务级模型**
> （`SubAgentActivityState` → `List<SubAgentTaskInfo>`），我们拿到的是**"模型调了哪个工具、返回了什么"**
> （AG-UI 的工具事件），于是我们把工具调用**一对一**渲染成卡片，而 Muse 把任务渲染成**时间线**。
> 样式是结果，模型是先因。

证据分级：`observed` = 反编译/代码里读到的；`inferred` = 由此推出的判断。

---

## 一、Muse 的模型（observed）

从 `com.facebook.aura.conversation` 反编译（jadx，2026-10-02）：

```
repo/SubAgentActivityState  { status: ACTIVE|COMPLETED, tasks: List<SubAgentTaskInfo>, startedAtMs: Long }
repo/SubAgentTaskInfo       { id, title, subtitle, isDone }
repo/SubAgentActivityStatus = ACTIVE | COMPLETED          （只有两态）
viewmodel/ActivitySubAgentRowUiModel { title, subtitle, isDone, showConnector }
view/HatchActivityCardKt + HatchActivityCardKt$DottedVerticalConnector$1$1
```

要点：
1. **有"一次跑动"这个对象**：`SubAgentActivityState` 带 `startedAtMs` —— 所以能显示"这次跑了多久"。
   它是一次 run 的容器，子任务挂在它下面。
2. **单位是任务，不是工具**：`SubAgentTaskInfo.title/subtitle` 是给人看的（标题 + 一句状态），
   `isDone` 是任务级完成度 —— 不是"某个工具返回了 200 字节"。
3. **状态只有两态**：`ACTIVE / COMPLETED`。简单到能一眼看懂 —— 不像工具调用那样有 loading/结果/错误三种杂音。
4. **列表由 repo 提供**（`conversation/repo/`）→ 即**服务端**把任务流按结构推下来，客户端只负责画。
5. **有连接线**：`ActivitySubAgentRowUiModel.showConnector` + `DottedVerticalConnector` 实现
   —— 行与行之间画虚线，视觉上就是**一条时间线**（"这几个是一串的"）。

## 二、我们的模型（observed）

`apps/mobile/src/`：
- 渲染单元是**工具**：`search-tool-card` / `browser-tool-card` / `mail-tool-card` / `jev-tool-card` /
  `browser-action-card` / `thread-artifacts(FileThreadCard|TaskThreadCard)` / `agent-ui(ArtifactCard|TaskCard)`。
- 聚合层只有 `running-tasks.tsx`，而它自己的注释写得很清楚：
  > "对应 Muse 的 SubAgentRow / activeSubAgents……我们的**后台任务（派活）**本来就在并行跑，
  > 但只出现在动态页——这里把它们带回聊天"
  也就是说：**我们把 Muse 的"本次跑动的子代理行"，映射成了"我派出去的后台任务"**（inferred：这正是差距的起点）。
- 数据源：聊天跑动走 AG-UI / CPK 事件流 —— 我们能拿到 `toolName` / `args` / `result` / `status`，
  **没有**"任务"这一层。任务（派活）是另一套 `task` 对象，属于后台作业，不属于本次对话轮次。

## 三、逐条差距（observed 对照）

| 维度 | Muse | 我们 | 用户感受 |
|---|---|---|---|
| 单位 | 任务（title+subtitle+isDone） | 工具调用（工具名+参数+结果） | "他给我看的是它调了啥，不是它在干什么" |
| 分组 | 一次 run 一个容器（含开始时间） | 卡片散落在消息流里，没有 run 边界 | 看不出"这一段是一件事" |
| 状态 | ACTIVE/COMPLETED 两态 | 每卡 loading/结果/错误 三态混杂 | 状态噪声大 |
| 时间 | 有 startedAtMs → 可显示用时 | 无 | 不知道跑了多久 |
| 视觉 | 行 + 虚线连接器 = 时间线 | 一张张并列的卡 | 不像"流"，像"一堆附件" |
| 文案 | 一句人话 subtitle | 工具名 + 结果片段 | 需要自己翻译 |
| 数据来源 | 服务端推结构（repo） | 客户端从工具事件**反推** | 客户端各自造轮子 |
| 子代理 | 是"本次跑动的并行分支" | 是"用户派出去的后台任务" | 概念都不一样 |

## 四、为什么会变成这样（inferred，逐条给依据）

1. **数据源不同，决定了天花板。** Muse 的服务端有自己的任务/子代理模型并**按结构下发**；
   我们的跑动走 AG-UI/CPK，协议里只有工具调用。我们没能（或没去）在服务端**聚合出 run 这一层**，
   于是客户端只能按"工具"建渲染器 —— 数量多、样式杂、语义浅。**这是根因。**
2. **我们按"工具"建渲染器 = 按实现建 UI。** 每接一个新工具就多一张卡（现在 7 张），
   而 Muse 是**一套**模型驱动一套行样式 —— 它的扩展成本在服务端，我们的在客户端 × 每个工具。
3. **把"子代理行"错映射成"派活任务"。** 名字像（都有 task/agent），语义不同：
   Muse 的是本次 run 的并行分支，我们的是用户显式派出的后台作业。映射一错，
   聊天里就永远长不出"本次跑动的过程"，只能长出"我的后台任务列表"。
4. **前几轮做的是"广度"不是"形态"。** 我们一直在补"这张卡要显示什么字段"（工具结果、附件、预览……），
   没有人回头定"一次跑动应该长什么样"。广度堆到一定程度，形态的缺失反而更明显。
5. **没有 run/activity 这个对象，就没有承载点。** 用时、连接线、两态、分组，全都需要一个
   "本次跑动"的对象才挂得住 —— 我们连这个对象都没有，所以这些不是"没做样式"，是"没有位置可放"。

---

## 五、要补什么（按依赖顺序，成本从低到高）

1. **服务端：把一次跑动聚合成一个 activity。** 在现有工具事件流外面包一层
   `runId / startedAtMs / status(ACTIVE|COMPLETED)`，并**把工具调用归并成任务**
   （同一子目标的连续调用合成一条，subtitle 用一句人话）→ 下发结构，客户端不改也能先跑通。
2. **客户端：加一个 activity 卡**（行 = 任务：title / subtitle / isDone；run 级别显示用时与状态；
   行间虚线连接器）。工具卡从"主角"降级为**点开任务后**的详情（现在的内容不浪费）。
3. **状态收敛成两态**（ACTIVE/COMPLETED），把工具的三态噪声收进详情里。
4. **子代理行回到它的本义**：属于本次 run 的并行分支才进 activity；用户派出的后台任务留在
   RunningTasks（那一栏已经有它的位置，不动它）。
