## 2. 本次交付（P0：工具执行收口）

### 目标
把**两个引擎**（自带 `conversation.ts` 与 `mastra-engine.ts`）的工具调用，统一收口到**一个执行咽喉**上；该咽喉是后续审批/密钥注入/脱敏/审计/污点的唯一挂载点。

### 为什么
调研报告 §4.1：nanoMuse 的 agent 主循环里**零 `.execute(`**，唯一执行路径是 `sentinel.guard(call, tool)`；真正执行只发生在闸门内部。OpenMuse 现在两套引擎各自直接调工具，安全策略无处挂载，也没法统一下发审批。

### 具体要求
1. 新增一个模块（建议 `apps/server/src/engine/tool-executor.ts`），对外只暴露一个入口，例如：
   `executeTool({ tool, call, owner, threadId, signal }) → ToolResult`
   内部按固定顺序走：**拒绝名单 → 调用方可覆写的逐次评估 → 放行 → 真正执行 → 结果脱敏 → 审计**。
2. 允许**工具自己**声明本次调用的危险性（这是关键设计，别省）：
   - 静态档位：`risk: "safe" | "moderate" | "sensitive"`（工具元数据）
   - 逐次覆写：`assess(args) → { risk?, egress?, egressTarget?, target?, summary?, warnings? }`
3. 两个引擎都改为**只能经这个入口**执行工具；`grep -rn "\.execute(" apps/server/src` 的结果里，除该模块内部外不应再有工具执行点（请在回报里贴出这条命令的输出）。
4. **审批钩子先留空实现**（本次不做 UI 往返）：当 `assess()` 判定需要批时，默认返回「拒绝 + 明确理由」，并把理由回灌给模型（模型应被明确告知「不要重试同一调用」）。审批的真正往返是下一单（P1）。
5. **行为兼容**：现有工具在没有任何 `assess()` 覆写时，必须与今天的行为**逐字一致**（包括错误信息、返回值形状、日志）。这是本次最重要的验收点。

### 测试（必须新增，且先红后绿）
- 未声明风险的工具：行为与改造前一致（对照既有测试断言）。
- 静态 `sensitive` 的工具：默认被拦，且返回给模型的文案包含「不要重试」。
- `assess()` 声明 `warnings` 的工具：即便调用方放行，也必须拦。
- 引擎接线：两个引擎各有一条用例证明「工具确实经过咽喉」（例如咽喉被调用过、或注入一个假工具观察记录）。
- 把「收口」变成可回归的守卫：一条用例断言 `apps/server/src` 里除咽喉外不存在裸工具执行点。
